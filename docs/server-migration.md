# План переезда на свой сервер

Статус: **план, не начат** (ноябрь 2026). Решено начинать до запуска 1 декабря: лимиты Supabase Free не выдержат нескольких игр одновременно. Клип в сторис Telegram от переезда не зависит (Supabase Storage). Документ — рабочий: агент отмечает выполненное (`[x]`) и дописывает решения по ходу.

## 0. Зачем и что получит игрок

Сейчас матч считает телефон режиссёра (хоста), а сообщения пересылает Supabase Realtime. Замеры (ноябрь 2026, модели в `packages/net` и Chromium с замедлением процессора):

- расчёты на хосте не тормозят: шаг мира в среднем 0,02 мс, худший ~7 мс (на телефоне ×5 — всё равно ничтожно); отрисовка держит 60 кадров при процессоре, замедленном в 6 раз;
- тормозит сеть и телефон хоста в роли «часов» и «пересылки»:
  - у гостя на мобильной сети со всплесками задержки показ отстаёт до 0,8 с и держится почти минуту (запас сокращается на 10 мс в секунду), 3% кадров стоят, 3% — рывок вперёд;
  - при отставании больше `LAG_GRACE_MS` (0,6 с) нажатия засчитываются поздно — «не успеваю нажать»;
  - моргнула сеть у гостя — пропущенные события теряются навсегда (полный снимок гость просит только при перезагрузке страницы): мир стоит, потом прыгает, «Море волнуется» может не прийти;
  - подвис кадр у хоста больше 0,2 с — Phaser выбрасывает это время, мир хоста отстаёт, у гостей замирания; хост свернул игру — стоят все, пока роль не передастся (5 с и больше), и дубль начинается заново;
- Supabase Free: ~40 сообщений/с на игру вчетвером при лимите 100/с на весь проект (при превышении отключает всех) — три одновременные игры положат все; 2 млн сообщений в месяц ≈ 160 матчей.

После переезда:

- матч считает сервер в Европе, телефон режиссёра — обычный игрок; сворачивание, подвисание и уход режиссёра никому не мешают, дубль не перезапускается;
- путь действия до других — 2 перехода «телефон ↔ сервер» вместо 4; обновления 10–20 раз в секунду вместо 5 — чужие видны с отставанием ~0,15–0,25 с вместо 0,3–0,8;
- моргнула сеть — игрок сразу получает снимок мира и продолжает;
- честнее: у режиссёра нет преимущества в задержке, и «кто живой» не лежит в памяти его телефона;
- нет лимитов на сообщения; видно, что происходит у игроков (ошибки, задержка, отвалы).

Песочница `/sandbox` и одиночный HTML не меняются: они работают без сети на `LocalSession`.

## 3. Игровой сервер (`apps/server`)

### 3.1 Состав

- Node 22, TypeScript strict, `ws`, `zod` (уже есть в `packages/net`), `pino` (логи JSON в stdout), `prom-client` (метрики), `@sentry/node` с DSN Bugsink, `jose` (токены).
- HTTP:
  - `POST /v1/auth/anon` → `{ userId, token }`;
  - `POST /v1/rooms` (создать);
  - `GET /v1/rooms/:code` → `{ wsUrl, status, players }` — для входа и превью ссылки;
  - `POST /v1/telemetry` — итоги сети за матч;
  - `POST /v1/errors` — туннель для ошибок с телефонов в Bugsink, чтобы блокировщики рекламы их не резали;
  - `GET /healthz`, `GET /readyz`;
  - `/metrics` — только во внутренней сети.
- WebSocket `/i/<экземпляр>/ws` — первое сообщение `{ t: 'hello', token, code, v }`. Токен не кладём в адрес: адреса попадают в логи.

### 3.2 Комната

`RoomManager` в памяти. Комната — это:

- состав, цвета, «Готов», настройки, режиссёр;
- статус `lobby | playing`;
- `MatchRunner`.

Что переносится из Supabase RPC:

| Было (Supabase) | Стало (сервер) |
|---|---|
| `create_room`, `join_room` (`room_full`, `room_playing`, `room_not_found`) | сообщения `create` / `join` |
| `leave_room`, `rename_member`, `update_room_settings` | `leave`, `rename`, `settings` |
| `kick_member` | `kick` |
| `set_room_status` | `start` |
| `room_preview` | `GET /v1/rooms/:code` |
| Presence (кто онлайн, «Готов») | само WebSocket-соединение; оборвалось — место держится 75 с для переподключения |
| `touch_room` (пульс) | ping/pong WebSocket |
| `claim_host` и `resumeMatch` после ухода хоста | не нужны: режиссёр — только роль в лобби; ушёл — роль переходит к следующему, матч идёт |
| уборка `pg_cron` | таймеры сервера: лобби без действий 30 мин, комната старше 6 ч — закрыть |

Правило 2 сохраняется:

- сервер знает всё;
- каждый игрок получает свою сущность только личным сообщением;
- в `hit` по игроку нет `attacker`.

Тест утечек (`netplay.test.ts`) переносится на сервер.

### 3.3 Матч

- `HostSession` становится «безголовым» хостом (`HeadlessHost`): `MatchSim` без своего игрока, все игроки — удалённые. Код рассылки (`ev`, `st`, `snap`, `me`, `reveal`, `match_end`) берётся как есть.
- **Часы — реальное время.** Цикл на `setInterval` с поправкой по `performance.now()`: если шаги отстали, догоняем пачкой. Время мира не теряется, как теряется у Phaser в браузере хоста.
- Пакеты событий каждые 100 мс (`cmdBatchMs` для сервера). Лимитов на сообщения больше нет; на гостя ~1–2 КБ/с.
- **Защита от пропусков:**
  - у каждого сообщения игроку есть номер (`seq`);
  - гость видит дыру или переподключился — шлёт `resync`, сервер отвечает полным снимком (есть сейчас: `sendResync`);
  - тест: обрыв на 1–5 с посреди «Море волнуется» → команда видна, мир совпадает с сервером.
- **Окно прощения по игроку:** `LAG_GRACE_MS` = измеренная задержка игрока (ping + отставание показа, которое гость сообщает в `ping`), не больше 1000 мс.
- **Запас задержки у гостя:** считать по реальному разбросу прихода пакетов за последние ~10 с (перцентиль), быстро сокращать после всплеска. Это правка `RemoteSession`, полезна и для старой схемы.
- Ограничения: на соединение — не больше 30 сообщений/с (лишнее отбрасываем, после 3 нарушений — закрываем); с одного IP — не больше 20 соединений и 10 новых комнат в минуту; размер сообщения ≤ 4 КБ.

### 3.4 Деплой без обрыва матчей (синий/зелёный)

- На `game` два контейнера: `game-blue` и `game-green`. Caddy ведёт `/i/blue/*` и `/i/green/*` на свой контейнер.
- Справочник `rooms_directory` (код → экземпляр) в базе, код уникален.
- Новая версия поднимается во втором цвете. После `readyz` новые комнаты идут в неё (`POST /v1/rooms` и справочник смотрят на «активный» цвет — файл в общем томе или запись в базе).
- **Старый экземпляр «досиживает»** (SIGTERM → режим drain):
  - новых комнат не принимает;
  - идущие матчи доигрывает;
  - комната, вернувшаяся в лобби, **переезжает**: старый экземпляр передаёт снимок лобби новому (состав, цвета, настройки, счёт, режиссёр) по внутреннему HTTP; клиенты получают `{ t: 'move', wsUrl }` и переподключаются — для игрока это доля секунды;
  - через 20 мин всё оставшееся переезжает принудительно; матч, если он ещё идёт, прерывается — это редкость, о ней пишем в лог.
- Сервер упал целиком — комнаты пропали. Клиент показывает «Связь с площадкой потеряна» и кнопку «Создать свою». Docker перезапускает контейнер, тревога уходит в Telegram.

### 3.5 Хранилища (`packages/store`)

- Интерфейсы:
  - `RoomDirectory` (`claim(code, instance)`, `lookup`, `release`, `move`);
  - `Telemetry` (`saveMatchNet`);
  - `Analytics` (`event`);
  - `Users` — пока только учёт выданных анонимных id, задел под аккаунты.
- Реализация на Kysely: `PostgresDialect` (прод), `SqliteDialect` (тесты, локальный запуск без базы). Миграции — Kysely Migrator, файлы в `packages/store/migrations`, запускаются отдельным шагом деплоя до переключения цвета; только «расширяющие» изменения (новые столбцы и таблицы), удаление — в следующем релизе.
- `game-core` не трогает базу (правило 1 сохраняется).

### 3.6 Тесты сервера

- Юнит: комната (вход, полный, идёт игра, кик, смена режиссёра, таймеры закрытия), авторизация, ограничения.
- Сетевой стенд в памяти (как `netplay.test.ts`): сервер + 4 клиента на `RemoteSession`, задержка/потери/обрывы. Проверки:
  - нет утечки игроков;
  - позиции совпадают;
  - нет откатов своего персонажа;
  - resync после обрыва;
  - переезд комнаты при drain.
- Нагрузочный (`apps/server/scripts/load.ts`): 200 комнат × 4 бота-клиента 10 минут, шаг мира p99 < 5 мс, задержка рассылки p99 < 20 мс, память стабильна.
- Плохая сеть: прогон в Actions с `tc netem` (задержка 100 ± 80 мс, потери 3%, обрывы).

## 4. Клиент (`apps/web`)

- **Интерфейс бэкенда комнат.** Логику `net/room.ts` (вход, состав, «Готов», старт, кик, переименование, настройки) вынести за интерфейс `RoomBackend`:
  - `SupabaseRoomBackend` — нынешний код, на время переезда;
  - `ServerRoomBackend` — WebSocket к `api.<домен>`.
  - `RoomClient`/`HomeClient` работают с интерфейсом.
- **Выбор сервера:**
  - создание комнаты — по `NEXT_PUBLIC_BACKEND` (`supabase | server`) и `?server=new` / `?server=old` для проверки;
  - вход по ссылке — `GET /v1/rooms/:code`; 404 → Supabase (старые комнаты доживают).
- **Игра:** у всех `RemoteSession` (у режиссёра тоже) поверх `WsTransport`. Логика смены хоста в клиенте для нового бэкенда не нужна.
- **Вход:** токен нового сервера в `localStorage['kto:auth2']`; один телефон — один игрок; `?player=N` для тестов сохраняется.
- **Превью ссылок:** `lib/preview.ts` → `GET /v1/rooms/:code` (с запасным путём на Supabase на время переезда).
- **Ошибки:** `@sentry/browser` с DSN Bugsink через туннель `/v1/errors`. Карты исходников загружаются при сборке образа `web` в Actions — проверить поддержку в версии Bugsink; если нет — без них.
- **Статистика сети:** в конце матча — ping, отставание показа, запас задержки, замирания, переподключения, модель/браузер (из User-Agent), PWA или вкладка → `POST /v1/telemetry`.
- **Не ломать:**
  - разблокировку звука и защиту от зума;
  - «Поделиться» из свежего жеста;
  - `lib/bot.ts` — превью-боты не подключаются к WebSocket;
  - CSP (`connect-src` += `wss://api.<домен>`);
  - сервис-воркер (не кэшировать `/v1/*`).

- **OpenTofu:**
  - серверы `game` и `infra` из `ubuntu-24.04` с cloud-init (только SSH-ключ и пользователь);
  - сеть `10.0.0.0/16`;
  - отдельный сетевой диск для данных `infra` — данные переживают пересоздание сервера;
  - облачный файрвол Timeweb: `game` — 22, 80, 443; `infra` — 22, 80, 443; внутренняя сеть открыта между ними. Порты Postgres, VictoriaMetrics, VictoriaLogs, Bugsink наружу не открыты.
- **Ansible:** идемпотентный, прогон из Actions по SSH (ключ в секретах). Приёмка — второй прогон подряд даёт `changed=0`. Перед применением — `--check --diff` в логе.
- **Мониторинг:**
  - метрики игры: комнаты, игроки, соединения, шаг мира (гистограмма), задержка рассылки, размер очередей, resync, отказы ограничений, переезды комнат;
  - системные метрики через node-exporter, контейнеры через cAdvisor;
  - статистика сети игроков из базы — в Grafana через Postgres-источник.
- **Тревоги** (vmalert → Alertmanager → Telegram):
  - `game` не отвечает;
  - p99 шага мира > 20 мс;
  - ошибок в Bugsink > N за 10 мин;
  - диск > 80%;
  - копия старше 26 ч;
  - сертификат < 14 дней;
  - медиана отставания показа у игроков > 500 мс за 15 мин.
- **Gatus:** проверяет `https://massovka.fun`, `api/healthz`, WebSocket-рукопожатие и страницу превью; страница `status.<домен>`.
- **Сторож за `infra`:** `.github/workflows/watchdog.yml` каждые 10 мин проверяет `status.<домен>` и `api/healthz`; две неудачи подряд — сообщение в Telegram напрямую через Bot API.
- **Копии:**
  - Postgres — `pg_dump` каждую ночь → restic в Object Storage (другой город);
  - хранение: 7 дневных, 4 недельных, 6 месячных;
  - метрики и логи не копируем — их можно потерять, дашборды лежат в репозитории.
  - `backup-check.yml` раз в неделю восстанавливает последнюю копию во временный Postgres в Actions и проверяет таблицы.
- **Доступ к админкам:** Grafana и Bugsink — их собственный вход + basic auth в Caddy; пароли в GitHub Secrets.

## 7. Безопасность — чек-лист

- [ ] SSH только по ключу, вход root запрещён, пользователь `deploy` с sudo по ключу; fail2ban; порт 22 закрыт в облачном файрволе для всех, кроме диапазонов GitHub Actions — если окажется слишком широко, оставить открытым с ключом + fail2ban.
- [ ] Автообновления безопасности (`unattended-upgrades`), перезагрузка ночью при необходимости — только `infra`; `game` — по команде из `ops.yml`, через drain.
- [ ] Контейнеры не от root, только нужные `volumes`, `read_only` где можно; базовые образы с фиксированной версией; Renovate или Dependabot для обновлений.
- [ ] Наружу: только 80/443 (Caddy) и 22. База, метрики, логи — только внутренняя сеть.
- [ ] Токен игрока подписан (Ed25519), ключ только в секретах; сервер не доверяет полям клиента (zod на всё входящее, как сейчас у хоста).
- [ ] Ограничения частоты (§3.3); базовая защита от DDoS у Timeweb есть (проверить, что включена).
- [ ] Логи без токенов и IP в открытом виде (IP — хэш с солью, для ограничений — в памяти).

## 10. Риски

| Риск | Что делаем |
|---|---|
| Иностранная карта не проходит у Timeweb | СБП/российская карта; иначе Selectel или Yandex Cloud — меняется только OpenTofu-модуль, Ansible от провайдера не зависит |
| Сервер в России не может скачать образы или пакеты (Docker Hub, ghcr.io, npm под ограничениями) | образы стека зеркалим в GHCR при сборке; проверить `docker pull` с сервера на этапе 2; запасной путь — свой реестр на `infra` |
| Игроки вне России (Турция, Европа) | Казань для них ~60–80 мс — играбельно; если их станет много — второй `game` в Timeweb Франкфурт/Амстердам (справочник комнат готов), но эти IP тоже проверить из России |
| Пока живём на Supabase и Vercel (AWS) — их могут начать резать в России | если российские игроки жалуются на обрывы без VPN — это знак ускорить переезд; Supabase Pro проблему не решает |
| Один игровой сервер — одна точка отказа | Docker перезапускает за секунды; тревога; второй `game` в другом городе — следующий шаг, справочник комнат к этому готов |
| Деплой посреди матча | синий/зелёный с drain (§3.4), проверка в этапе 3 |
| iOS рвёт соединение в фоне | `seq` + resync, место держится 75 с |
| Агент не видит серверы напрямую | всё через Actions + `ops.yml`; логи и метрики — через `ops.yml logs` и Grafana-снимки в сводке задачи |
| Утечка секретов | только GitHub Secrets, в логах Actions — маскирование; ротация описана в `infra/README.md` |
| Двойная поддержка старой и новой схемы | только на время этапов 4–5, Supabase-код не развиваем |
