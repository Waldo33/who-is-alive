# Безопасность: модель угроз, правила, что делать при утечке

Ревью безопасности — 26.11.2026 (Claude Doc «Массовка — AppSec-ревью»), исправления — PR 54 и следом.
Этот файл — то, что держать в голове при каждой новой фиче. Регрессии ревью — `apps/server/test/security.test.ts`,
`apps/server/test/bot.test.ts`, `infra/test/caddy-config.sh`, `infra/test/workflows-check.py`.

## 1. Что защищаем

У игры нет денег и личных данных: игроки анонимные, имена — до 14 знаков. Поэтому по важности:

1. **Инфраструктура** — `TWC_TOKEN` (облако, DNS, S3, из него же выводится SSH-ключ root ко всем машинам),
   ключи ботов, ключи S3. Утечка = чужой человек управляет продом.
2. **Доступность матчей** — 2–4 друга играют 5 минут; сервер не должен падать или тормозить от одного злого клиента.
3. **Бренд и бот** — карточки «через бота» в чатах Telegram, чат тревог, превью ссылок: ими нельзя рассылать
   чужие ссылки и спам от имени игры.
4. **Честность игры** — «никто не знает, кто игрок» (правило 2 в CLAUDE.md), матч считает сервер.

## 2. Границы доверия

```
телефон ──HTTPS/WSS──> Caddy (Европа) ──127.0.0.1──> игра (синий/зелёный)
                         │  /tg/*  ──туннель SSH──> Caddy :8080 (Нидерланды) ──> бот
Нидерланды ──туннель──> Европа: база :5432, node_exporter :9100, вход :8079 (только /metrics, /v1/events, /internal/errors)
GitHub Actions ──SSH (ключ из TWC_TOKEN)──> обе машины
```

- **Всё, что пришло с телефона, — чужое**: тело, заголовки, номер попытки, подпись карточки, текст ошибки, имя,
  id устройства. Сервер проверяет и решает сам; телефон только просит.
- **Адрес игрока** — из `X-Forwarded-For`, который ставит Caddy (`TRUST_PROXY=1`). Через туннель к боту адрес
  несёт `X-Massovka-Client`, внешний такой заголовок Caddy перезаписывает.
- **«Изнутри машины»** (`internal()` в `server.ts`) — петля и без чужого адреса в `X-Forwarded-For`. Внутренние
  маршруты (`/internal/*`, `/metrics`, `/tg/setup`, `/tg/status`) — только так, снаружи 404.
- **CI** — граница доверия тоже: workflow из любой ветки исполняет код с правами секретов, которые ему видны.

## 3. Правила для нового кода

Короткая версия — в CLAUDE.md («Безопасность»). Подробнее:

- **Авторизация на объекте, а не «есть токен».** Токен игрока выдаётся любому — он отвечает на вопрос «кто ты»,
  а не «можно ли тебе». Менять чужое (обложка клипа, итог загадки, комната) — только владельцу/участнику.
- **Лимиты на всё, что можно перебрать или размножить**: коды комнат, загрузки, тапы загадки, снимки мира.
  Лимит по игроку не спасает — токенов сколько угодно; нужен и по адресу (`RateWindow` в `limits.ts`).
  За одним адресом бывает компания или оператор — лимит по адресу щедрый, строже только на промахи.
- **Счёт ведёт сервер.** Номер попытки, «угадал ли», очки, «кто выбыл» — считаются на сервере; число с телефона —
  только подсказка (повтор того же запроса).
- **Текст с телефона, который уходит дальше** (Telegram, чат тревог, карточка, фильм): без чужих ссылок и
  @упоминаний (`safeCaption` в `bot.ts`), без невидимых и «переворачивающих» символов (`cleanName` в `room.ts`).
- **Новое сетевое поле** — проверь на утечку «кто игрок» (`packages/net/test/netplay.test.ts`).
- **Пути и имена файлов** — только из строгого шаблона (`CLIP_ID`, `PUZZLE_CODE`) или `inside(resolve(...))`.
- **SQL** — только параметры; подстановка в текст запроса — только константы кода.
- **Процессы** — `spawn` без shell, аргументы массивом.
- **Ошибки наружу** — без стека и внутренних адресов: `{ error: 'код' }`.
- **Каждое исправление безопасности — с тестом**, который падал бы до него.

## 4. CI и выкладка

- **Секреты прода — только в окружении `production`** (Settings › Environments), а оно пускает только ветку
  `main`. Каждая задача workflow, которая читает секреты, объявляет `environment: production`; workflow с
  секретами не запускаются на `pull_request` и на push в другие ветки. Проверяет `infra/test/workflows-check.py` в CI.
  Поэтому сухой прогон Ansible и план Terraform — после push в `main`, а `infra-logs` — только кнопкой.
- **Сторонние actions — по полному SHA** с тегом в комментарии; обновляет Dependabot (`.github/dependabot.yml`).
- **Ничего «последней версии»**: Node, Caddy, node_exporter, VictoriaMetrics/Logs, Grafana, GeoIP — версии и
  SHA-256 в `infra/game/versions.env`. Обновить: новая версия + сумма из файла сумм релиза, сверить со скачанным
  файлом, PR. CI проверяет Caddy той же версией.
- `pnpm audit --prod --audit-level critical` в CI.
- Логи Actions публичны для всех с доступом к репозиторию: секреты не печатать, ответы API с паролями — тоже.

### Настройка окружения (один раз, владелец)

1. Settings › Environments › New environment → `production`.
2. **Deployment branches and tags** → «Selected branches and tags» → добавить `main`.
3. В этом окружении — **Environment secrets**: `TWC_TOKEN`, `TELEGRAM_BOT_TOKEN`, `ALERTS_BOT_TOKEN`,
   `GRAFANA_PASSWORD`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` (значения те же, что сейчас в Settings › Secrets › Actions).
4. Запустить любую выкладку с `main` (Actions › game-deploy › Run workflow) — должна пройти.
5. Удалить эти же секреты из **Repository secrets** (Settings › Secrets and variables › Actions). Пока они там,
   их видит любой workflow любой ветки — окружение защищает, только когда репозиторных копий нет.
6. Окружение `probe` (осталось от проверки 26.11) можно удалить.

Если пункта «Deployment branches» нет — тариф GitHub не даёт правил окружений приватному репозиторию
(нужен Pro); тогда секреты остаются в репозитории, а защита — только порядок «не пушить чужой код».

## 5. Если ключ утёк

| Ключ | Где живёт | Как сменить |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` (игровой бот) | GitHub, сервер в Нидерландах | BotFather › `/revoke` → новый в секрет → `game-deploy` (вебхук и его секрет перепривяжутся сами) |
| `ALERTS_BOT_TOKEN` (бот тревог) | GitHub, `/etc/massovka` в Нидерландах | так же в BotFather → секрет → `game-deploy` |
| `TWC_TOKEN` | GitHub (окружение `production`) | панель Timeweb › API → новый токен → секрет в `production` → `game-deploy` → старый токен удалить в панели. SSH-ключ выкладки выводится из токена: первая задача выкладки (`keys`, `infra/game/keys.py`) сама ставит новый ключ на оба сервера через API Timeweb и убирает старые ключи выкладки с серверов и из аккаунта |
| `S3_ACCESS_KEY`/`S3_SECRET_KEY` | GitHub, `secrets.env` в Европе | панель Timeweb › хранилище › ключи → секреты → `game-deploy` |
| `GRAFANA_PASSWORD` | GitHub, Grafana | новый секрет → `game-deploy` (пароль admin перезапишется) |
| `AUTH_SIGNING_KEY` (токены игроков) | `/etc/massovka/secrets.env` в Европе | удалить строку и перезапустить выкладку — родится новый; все игроки молча получат новые токены |
| пароль базы, `LOAD_KEY` | `secrets.env` | удалить строку → выкладка родит новый |

После любой смены — `infra-check` и живой прогон (`game-deploy` гоняет его сам).

**Смена `TWC_TOKEN` по шагам** (так прошла 26.11.2026, после неё и появилась задача `keys`):
1. Timeweb › API — выпустить новый токен (старый пока не трогать).
2. Settings › Environments › `production` — заменить `TWC_TOKEN`.
3. Actions › game-deploy › Run workflow. Задача `keys`: «новый ключ отправлен на сервер» для каждого сервера,
   «старых ключей выкладки убрано: 1», дальше выкладка как обычно.
4. Timeweb › API — удалить старый токен. Нового значения старого токена не бывает: перевыпуск — это новый ключ.
Если Timeweb не поставил ключ — сервер › SSH-ключи в панели, ключ `massovka-actions-<дата>`, и снова выкладка.

## 6. Что сознательно оставлено

- Анонимный токен на 400 дней без отзыва (L8): ничего ценного не открывает.
- Античит в рамках жанра (L1): поправка на лаг до 600 мс, автокликер.
- SSH-ключ и пароль базы «только чтение» выводятся из `TWC_TOKEN` (N4): кто владеет токеном, и так владеет
  машинами через API Timeweb (пересоздать, сбросить пароль root), отдельный ключ здесь мало что даёт.
- Содержимое клипа в S3 не проверяется (телефон кладёт его по подписанной ссылке): ограничено размером,
  типом, лимитами по игроку и адресу; файл живёт 2 суток.
- Grafana открыта в интернет с паролем; её туннель в Европу пускает только к метрикам, аналитике и ошибкам.
